---
title: Launching the Rover
description: One command to bring Viator up - checks, container, build, node graph and dashboard.
---

Getting Viator running is one command. SSH into the rover, run `make launch`, and you end up looking at the [dashboard](./dashboard.mdx) with the rover running behind it.

```bash title="Terminal"
ssh trickfire@192.168.0.112
cd ~/viator
make launch
```

The rover builds from the source tree on its own disk, so `make sync` your changes over (or pull them on the rover) and relaunch.

## What `make launch` does

Five phases, each reporting before it runs anything, so a failure tells you which link in the chain broke instead of leaving you to work it out:

```text
  viator  bringing the rover up

  [1/5] host
  [ ok ] docker                 28.3.1
  [ ok ] compose                v2.33.0
  [ ok ] workspace              /home/trickfire/viator (main @ a1b2c3d)
  [2/5] can bus
  [ ok ] can1                   up at 1000000 bit/s
  [3/5] container
  [ ok ] image viator:dev       done
  [ ok ] container viator       done
  [4/5] workspace
  [ ok ] colcon build           12 packages
  [5/5] rover
  [ ok ] node graph             running as pid 487
```

| Phase       | Does                                                                            |
| ----------- | ------------------------------------------------------------------------------- |
| `host`      | Docker is installed and its daemon is reachable, and reports which commit you're about to run |
| `can bus`   | `can1` is up at 1 Mbit, and brings it up if it isn't                            |
| `container` | Builds the `viator:dev` image if anything changed, and starts the container      |
| `workspace` | `colcon build` inside the container                                              |
| `rover`     | Starts the node graph, then opens the dashboard on top of it                      |

Then it hands you the dashboard. Press `?` in there for the keys, `q` to quit.

<Callout type="info" title="It works from either side">
    Run it on the rover's host and it does all five phases. Run it inside the dev container, where
    the first four are already done, and it goes straight to the node graph and the dashboard.
    There is nothing to remember about which terminal you are in.
</Callout>

<Callout type="warning" title="Quitting the dashboard stops the rover">
    `make launch` owns the node graph it started, so `q` shuts it down, and so does losing your SSH
    session. That is the right behaviour on a bench, where a dropped connection should stop the
    motors rather than leave them holding a setpoint. To run the rover independently of your
    terminal, use `make graph` and `make tui` as [two separate commands](#running-it-without-the-dashboard).
</Callout>

## Make CAN bringup automatic

`make launch` brings `can1` up when it finds it down, which costs a sudo prompt every time. Do it once per rover and the bus is already up before anyone logs in:

```bash title="Terminal (on the rover)"
make can-service
```

That installs a systemd unit which runs `scripts/setup-can-network.sh` at boot, enables it, and starts it immediately. Safe to enable: it configures the interface and puts the drivebase controllers into speed mode, it does not command any motion.

The unit points at the checkout it was installed from, so if the repo moves, run it again.

<Callout type="idea" title="make can-setup is still there">
    For a one-shot bringup without touching systemd - a bus that dropped mid-session, or a machine
    you don't want to change - `make can-setup` does just the bringup.
</Callout>

## Flags

Pass these through `FLAGS=`:

```bash title="Terminal"
make launch FLAGS=-B      # skip the workspace build
```

| Flag | Does                                                                     |
| ---- | ------------------------------------------------------------------------ |
| `-B` | Skip `colcon build`. Relaunch without recompiling                        |
| `-v` | Stream the build output instead of collapsing it to a status line        |
| `-n` | Rebuild the container image with no build cache                          |
| `-c` | Force recreate the container                                             |
| `-s` | Skip the CAN check. The graph will shut down when `can_rmdx8` can't open the bus |

`-B` is the one you'll use most: once the workspace is built, `--symlink-install` means Python edits take effect without rebuilding, so relaunching is just the rover coming back up.

## The other commands

```bash title="Terminal"
make            # list every target
```

| Command       | Does                                                                   |
| ------------- | ---------------------------------------------------------------------- |
| `make launch` | Bring everything up and open the dashboard                             |
| `make status` | Check the rover is actually ready to drive                             |
| `make stop`   | Stop the node graph. Add `FLAGS=-d` to stop the container too          |
| `make tui`    | Open the dashboard against a rover that is already running             |
| `make graph`  | Run the node graph alone, in the foreground, no dashboard              |
| `make build`  | Build the workspace                                                    |
| `make connect`| Get a shell in the dev container                                       |
| `make can-service` | Make CAN bringup automatic at boot. Once per rover               |
| `make can-setup`   | Bring the CAN bus up right now, by hand                          |
| `make sync`   | rsync this checkout to the rover (`IP=`, `REMOTE_PATH=`)               |

`status`, `stop`, `tui`, `graph` and `build` all work from the rover's host and from inside the container - the ones that need ROS re-run themselves in the right place.

## Confirm it came up

`make launch` leaves you in the dashboard, where every module should reach `ok` within a few seconds:

```text
╭─ modules  8 reporting ───────────────────────────────────────────────╮
│  module                   state     detail                          │
│  arm                      ok        mode disabled                   │
│  camera                   ok        2 cameras: [0, 1]               │
│  can_rmdx8                ok        6 motors on can1                │
│  drivebase                ok        awaiting commands               │
│  heartbeat                ok        awaiting mission control        │
│  mission_control_updater  ok                                        │
│  rosapi                   ok        discovered                      │
│  rosbridge                ok        discovered                      │
╰──────────────────────────────────────────────────────────────────────╯
```

For the same answer without opening anything, from a second terminal:

```bash title="Terminal 2"
make status
```

```text
  viator  preflight

  [ ok ] image                  viator:dev
  [ ok ] container              viator running
  [ ok ] can1                   up at 1000000 bit/s
  [ ok ] motors                 all 6 responding
  [ ok ] cameras                2 video device(s): /dev/video0 /dev/video1
  [ ok ] rosbridge              listening on 9090
  [ ok ] disk                   42103 MB free on /home/trickfire/viator

  ready - 7 checks passed
```

It exits non-zero if anything failed, so you can gate a script on it. The `motors` check is the one worth caring about: it listens to the bus and names the CAN IDs that aren't answering, which is how you find a loose connector before a scored run rather than during one.

## Start mission control

Mission control lives in its own repo and runs on **your** machine, not the rover.

<Steps>
    <Step>
        If you don't already have it, clone
        [mission-control](https://github.com/TrickfireRobotics/mission-control) and install its
        dependencies:

        ```bash title="Terminal (your machine)"
        git clone https://github.com/TrickfireRobotics/mission-control.git
        cd mission-control
        npm install
        ```
    </Step>
    <Step>
        Start it:

        ```bash title="Terminal (your machine)"
        npm run dev
        ```
    </Step>
    <Step>
        In the settings tab, point the websocket at the rover's address - the same one you SSH
        into. The connection indicator turns green once the rover's `rosbridge_server` is up and
        reachable.
    </Step>

</Steps>

<Callout type="success" title="The full chain is live">
    Mission control's websocket indicator is green, `make status` says ready, and every module in
    the dashboard is `ok`. Rover hardware through to mission control.
</Callout>

## Running it without the dashboard

Use this when you want the rover to outlive the terminal you are watching it from, or you want the raw launch output rather than the dashboard's rendering of it.

<Steps>
    <Step>
        In one terminal, run the graph in the foreground:

        ```bash title="Terminal 1"
        make graph
        ```
    </Step>
    <Step>
        In another, attach the dashboard:

        ```bash title="Terminal 2"
        make tui
        ```

        This one only observes, so closing it or losing the connection leaves the rover running.
    </Step>
</Steps>

`make graph` doesn't check CAN or build anything - it assumes `make launch` already did. If the bus isn't up, `make can-setup` brings it up on its own.

## Watching the bus directly

When you suspect the problem is below ROS, watch the raw CAN traffic:

```bash title="Terminal 2"
candump any
```

`any` rather than a specific interface means this keeps working no matter which CAN line ends up carrying traffic, and it picks up traffic as soon as the interface comes up.

<Accordions>
    <Accordion title="make launch asks for sudo every time">
        It only does that when it has to bring the bus up itself. `make can-service` installs the
        systemd unit that does it at boot, after which `make launch` finds `can1` already up and
        never needs root.
    </Accordion>
    <Accordion title="can1: interface not present">
        There is no CAN hardware on this host, or the transceiver isn't powered. On the Orin, check
        the harness at the expansion header (see [Viator Orin](./orin.mdx)) and `dmesg` for the
        `mttcan` driver. On a laptop this is expected - the rover needs real hardware to run.
    </Accordion>
    <Accordion title="The node graph shut itself down during startup">
        A node that commands motors failed, and the launch file takes the whole graph down when
        that happens so the motors stop rather than holding their last setpoint. `make launch`
        prints the first error it finds; the full output is in `log/launch-latest.log`.
    </Accordion>
    <Accordion title="The build failed and I can't see why">
        Re-run with `make launch FLAGS=-v` to stream the build instead of collapsing it. On a
        failure the path to the full captured output is printed too.
    </Accordion>
    <Accordion title="Mission control's websocket indicator stays red">
        Check the address in mission control's settings matches the rover's current IP, and that
        `make status` reports `rosbridge listening on 9090`. If it doesn't, the graph isn't running.
    </Accordion>
    <Accordion title="candump shows no traffic">
        The bus isn't up, or nothing is driving it. `make status` tells you which: it reports the
        interface state and which motors are answering separately.
    </Accordion>
    <Accordion title="Permission denied talking to Docker">
        Your user isn't in the `docker` group. `sudo usermod -aG docker $USER`, then log out and
        back in.
    </Accordion>
    <Accordion title="A module shows degraded or stale">
        See [the dashboard page](./dashboard.mdx) - it covers every state and what to do about it.
    </Accordion>
</Accordions>
